# Резервные копии

Сервис `backup` в Docker Compose создаёт согласованную SQLite-копию через `VACUUM INTO` при запуске, затем раз в сутки. Рабочий том смонтирован только для чтения. Копии находятся в отдельном томе `doktor-ryadom_ryadom_backups`, каталог `/backups`, права файлов 0600. Сохраняются последние 14 копий; удаляются только файлы собственного формата имени.

Существующая внутренняя ежедневная копия приложения в `/data/backups` с хранением семь дней остаётся дополнительной копией в рабочем томе.

Каждая новая копия проверяется через `integrity_check` и `foreign_key_check`. При ошибке операция повторяется через 30 минут. Healthcheck становится неуспешным, если последняя копия старше 26 часов. Журнал содержит время и результат, без содержимого записей.

## Проверка восстановления

```sh
docker compose ps
docker compose logs --tail=20 backup
docker compose exec backup ls /backups
docker compose exec backup node scripts/check-backup.mjs /backups/ИМЯ-КОПИИ.sqlite
```

Последняя команда переносит выбранный файл во временный каталог, проверяет целостность, связи и доступность основных таблиц, затем проверяет запись и откат транзакции. Рабочая база не меняется; временная копия удаляется.

Полное восстановление сервиса сначала отработайте в изолированной среде с тем же образом: копия базы в отдельном томе, запуск миграций, вход и проверка данных без отправки писем или push. Заменять рабочую базу следует только после остановки приложения, сохранения текущей базы вместе с WAL и проверки выбранной копии. Это отдельная административная операция, её проверочный скрипт не выполняет.

## Что остаётся оператору

Оба Docker-тома находятся на одном сервере. Эта схема помогает при ошибке приложения, но не защищает от потери всего сервера. До реального запуска настройте защищённое внешнее хранение копий и контроль неуспешных healthcheck. Копии содержат чувствительные данные; доступ и срок хранения согласуются с правилами проекта.

## Выгрузка за пределы сервера (S3)

Сервис `offsite` в `compose.yml` берёт локальные копии из тома `ryadom_backups` (только чтение), шифрует каждую алгоритмом AES-256-GCM и загружает в бакет S3 (`petzy-1`, Backblaze B2, регион `eu-central-003`). В бакете остаётся одна последняя копия за каждый из последних 14 дней. Проверка раз в час.

- Секреты лежат в `.env.offsite` (права 600, не в git). Туда входят ключи S3 и `BACKUP_ENCRYPTION_KEY`.
- Бакет видит только шифротекст. Без ключа шифрования копии не расшифровать, поэтому ключ надо сохранить отдельно от сервера (менеджер паролей). Потеря ключа означает потерю копий.
- Регион бакета вне Казахстана: решение о трансграничной передаче принимает владелец и юрист. Пока это тестовые данные.
- Сервис `backup` по-прежнему без сети: выгрузкой занимается только `offsite`.

### Восстановление из бакета

1. Скачать и расшифровать нужную копию (переменные из `.env.offsite`, в вывод секреты не попадают):

   ```sh
   cd /home/ubuntu/pet/control-app
   set -a; . ./.env.offsite; set +a
   docker compose run --rm -v "$PWD/restore:/restore" offsite node scripts/offsite.mjs decrypt /restore/copy.enc /restore/ryadom.sqlite
   ```

   Файл `copy.enc` предварительно скачивается из бакета тем же клиентом, см. `s3Client` в `scripts/offsite.mjs`.
2. Проверить копию: `docker compose exec backup node scripts/check-backup.mjs /restore/ryadom.sqlite`.
3. Полное восстановление сначала в изолированном томе, затем замена рабочей базы при остановленном приложении (см. выше).

Проверено 16.10.2026: последняя копия из бакета расшифрована, контрольная сумма совпала с исходным файлом сервера.
