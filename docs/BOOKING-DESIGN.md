# Запись к врачу и переносимая карточка пациента: черновик дизайна

Статус: запись к врачу реализована в MVP (слоты, заявки, подтверждение, отмена, каталог с сортировкой, фильтрами и пагинацией; миграция `0018_booking.sql`). Перенос карточки с грантами и журналом открытий ещё не сделан. Прежний текст ниже остаётся черновиком этой части. Код не менялся, миграции не добавлялись, ничего не коммитилось. Юридические выводы требуют проверки юристом в Казахстане.

## 3. Сущности

Принцип: карточка принадлежит пациенту. Врач получает доступ через грант. Запись и доступ к карточке - два разных действия.

| Сущность | Владелец | Назначение | Ключевые поля (черновик) |
| --- | --- | --- | --- |
| `doctor_slots` | врач | Свободные окна приёма | `doctor_id`, `starts_at`, `ends_at` (UTC), `status` (open, held, booked, closed), `held_by`, `held_until` |
| `doctor_schedule_rules` | врач | Недельное расписание, из которого строятся слоты | `doctor_id`, `weekday`, `from`, `to`, `slot_minutes`, `tz` |
| `appointment_requests` | пациент | Запрос на конкретный слот | `id`, `patient_id`, `doctor_id`, `slot_id`, `reason` (короткий текст, без обязательных медданных), `status` (pending, confirmed, declined, cancelled, expired), `created_at`, `decided_at` |
| `appointments` | общая связь | Подтвержденный приём | `request_id`, `slot_id`, `patient_id`, `doctor_id`, `status` (scheduled, done, no_show, cancelled), `visit_note_id` (только у врача) |
| `card_versions` | пациент | Версионированная карточка | `id`, `patient_id`, `version`, `payload` (зашифрован), `created_at`, `reason` (что изменилось). Никогда не перезаписывается: новая версия = новая строка |
| `card_grants` | пациент | Доступ врача к версии карточки по согласию | `id`, `patient_id`, `doctor_id`, `card_version_id` (срез) или `mode` = live, `scope` (разделы), `consent_text_version`, `granted_at`, `revoked_at`, `revoke_reason` (manual, transfer, expired) |
| `card_access_log` | пациент виден | Кто, когда и что открыл | `grant_id`, `doctor_id`, `card_version_id`, `opened_at`, `section`. Без содержимого |
| `doctor_notes` | врач | Заметки врача, не переносятся | Остаются в своей таблице, в карточку пациента не попадают ни при каких условиях |

Связь с существующим кодом: `links` остается операционной связью «врач ведет пациента» (дневник, сводки, план). `card_grants` добавляется рядом, а не вместо `links`, чтобы не менять уже работающий доступ к сводкам.

## 4. Потоки

### 4.1 Пациент выбирает врача и записывается

1. Пациент открывает каталог (уже есть) и выбирает подтвержденного специалиста.
2. Видит свободные слоты в часовом поясе пациента (по умолчанию Asia/Almaty, как в `KAZAKHSTAN.md`).
3. Выбирает слот, пишет короткую причину (до 300 символов, предупреждение «не пишите диагноз, если не хотите»).
4. Создается `appointment_requests` со статусом pending, слот переходит в held на 24 часа. Врач получает уведомление без медданных.
5. Врач подтверждает, отклоняет или предлагает другой слот. Слот, не подтвержденный за срок, возвращается в open.
6. При подтверждении создается `appointments`. Доступа к карточке это не дает.

### 4.2 Пациент делится карточкой с врачом

1. После подтверждения записи (или до нее, если пациент хочет) пациент нажимает «Поделиться карточкой с врачом».
2. Показывается текст согласия с версией, разделы карточки и срок действия по умолчанию (до конца приёма + 30 дней, потом продление вручную).
3. Пациент подтверждает. Создается `card_grants` на текущую версию (срез).
4. Врач открывает карточку. Каждое открытие пишется в `card_access_log`.

### 4.3 Переход к другому врачу (перенос)

1. Пациент записывается к новому врачу (поток 4.1).
2. При подтверждении записи система предлагает: «Передать карточку новому врачу?». Старый врач по умолчанию теряет доступ к новым версиям.
3. Если пациент согласился, создается новый грант на срез текущей версии. Старому гранту ставится `revoked_at` с причиной `transfer`, если пациент не выбрал сохранить его.
4. Карточка не копируется в данные нового врача. Врач видит ее только по гранту и не может выгрузить как свою.
5. Заметки старого врача не передаются. Пациент может запросить у старого врача выписку по своим записям (правила выписки проверить юристом).

## 5. Правила согласия и отзыва

- Согласие на доступ отдельное: на конкретного врача, на конкретную версию (срез) или живой доступ, на разделы, с сроком.
- Запись к врачу не равна согласию на доступ к карточке. Врач видит только причину и время записи.
- Текст согласия имеет версию (`consent_text_version`). При изменении текста старые согласия не переносятся на новый текст автоматически.
- Отзыв: одна кнопка в карточке, действует сразу: новые открытия блокируются. Уже открытые данные врач не «забирает», но новых версий не видит.
- При отзыве врач получает нейтральное уведомление «доступ отозван», без причины.
- Врач не может сам продлить доступ. Продление делает только пациент.
- Экстренные ситуации в запись и доступ не входят. Текст об экстренных службах (103, 112) остается в настройках, как сказано в `KAZAKHSTAN.md`.
- Несовершеннолетние и законные представители в первой версии не поддерживаются. Это отдельная модель согласия.
- Психиатрические специальности (`specialty_kind = psychiatrist`) чувствительнее: доступ к карточке для них отдельный подтверждаемый шаг. Решение владельца в разделе 9.

## 6. Что хранить у пациента, что у врача

| Данные | У пациента | У врача | Переносится |
| --- | --- | --- | --- |
| Профиль «О себе» | да, основной источник | только то, что пациент показал по гранту | да, по гранту |
| Дневник (checkins) | да | только по существующей связи `links` | не в карточку; сводки по своей связи |
| Препараты, цели | да | видит по гранту | да, по гранту |
| Анамнез (анкета, которую заполнил пациент) | да | видит по гранту | да, по гранту |
| Документы, которые пациент загрузил | да | видит по гранту | по выбору раздела |
| План врача (`plans`) | копия итога, которую пациент получил | свой план | нет |
| Заметки врача, выводы приёма | нет | да | нет |
| Записи и статусы приёма | история у пациента | история у врача | нет |
| Журнал доступа | да, виден пациенту | нет | нет |

Причина: заметки врача относятся к его медицинской документации и не принадлежат пациенту. Пациент может получить их копию по своему запросу, а не через перенос.

## 7. Безопасность и хранение

- Локализация. Главный вопрос до работы с реальными пациентами. По найденной публикации, статья 12 закона 94-V требует хранить базу персональных данных на территории Казахстана. Закон 326-VIII от 24.06.2026 существенно обновил закон о персональных данных, большинство изменений вступило в силу 01.07.2026. Новая статья 10-1 требует уведомить уполномоченный орган до начала обработки и указать местонахождение базы. Точный текст действующей редакции в поиске не открылся, его нужно проверить по `adilet.zan.kz` или `zakon.uchet.kz` и подтвердить юристом.
- Практически это означает: карточка, записи, слоты и журнал доступа хранятся в Казахстане, резервные копии (см. `docs/BACKUPS.md`) тоже. Наличие HTTPS и резервных копий этого не подтверждает.
- Шифрование карточки в покое, ключи отдельно от базы. Поле `payload` в `card_versions` не должно читаться при обычных выборках и не должно попадать в логи.
- Журнал `audit` не пишет содержимое. Для `card_access_log` - только идентификаторы и раздел.
- Push и SMS: в тексте уведомлений нет диагноза, препаратов и причины визита. Пример: «Врач открыл ваш запрос на приём».
- Отзыв: проверка на сервере при каждом запросе карточки, без кэша на клиенте дольше сессии.
- Сверка с `GAP-CLOSURE.md`: восстановление доступа, удаление и экспорт аккаунта должны работать раньше записи. Без них перенос карточки создает риск невозможности вернуть данные пациенту.
- Защита от утечки через врача: врач не может экспортировать карточку, для просмотра используется интерфейс без кнопки «скачать». Это не полная защита: скриншот всегда возможен.

## 8. MVP (первый шаг)

Цель: проверить запись и перенос на одном сценарии с тестовыми данными, без реальных пациентов, пока не решен вопрос локализации.

Включаем:
1. Врач задает недельное расписание и длительность слота, закрывает даты. Слоты строятся на сервере.
2. Пациент выбирает подтвержденного врача из существующего каталога, слот и короткую причину. Статусы: pending, confirmed, declined.
3. Врач подтверждает или отклоняет запрос. Перенос слота по согласию: одна кнопка «предложить другое время», без автоматики.
4. Карточка пациента: существующий `profiles` плюс препараты и цели, версии при каждом сохранении (`card_versions`).
5. Грант врачу на срез текущей версии, отзыв одной кнопкой, журнал открытий для пациента.
6. Перенос: при смене врача новый грант и автоматический отзыв старого (по умолчанию).
7. Уведомления: только факт события, без медданных.

Тест: сценарий «записался к врачу А, поделился карточкой, отозвал, записался к врачу Б, карточка передана, врач А не видит новые версии, журнал виден пациенту».

## 9. Что НЕ делать в первой версии

- Оплату, подписки, комиссии за запись.
- Мгновенное бронирование без подтверждения врача.
- Видеоприём и чат с врачом до записи.
- Автоматический подбор врача и рейтинговую сортировку по медданным.
- Интеграцию с внешними клиниками, EHR и государственными системами (ЕМИАС-подобными, eGov) до отдельного решения.
- Экспорт карточки врачом, печать и отправку по почте.
- Перенос заметок врача и истории приёмов.
- Несовершеннолетних и законных представителей.
- Общий доступ нескольких врачей одновременно по умолчанию. Разрешить можно только явным выбором пациента, по одному гранту на врача.
- Напоминания SMS, пока нет настроенной доставки push и почты (см. `COMPETITOR-REVIEW.md`).

## 10. Решения владельца, с рекомендациями

Каждое решение дано с рекомендацией. Владелец может подтвердить одним словом «да» на каждый пункт.

1. Модель записи. Варианты: врач публикует слоты сам; пациент шлет запрос без слотов. Рекомендация: врач публикует слоты, пациент выбирает слот и отправляет запрос, врач подтверждает. Причина: врач контролирует нагрузку, и это не требует отдельной модели «пул врачей».
2. Мгновенная запись без подтверждения. Рекомендация: нет в MVP, добавить позже для врачей, которые сами этого хотят.
3. Оплата в первой версии. Рекомендация: нет. Пациент ничего не платит, запись бесплатна.
4. Кто платит за платформу. Рекомендация: в MVP платформа за счет владельца. Позже плата за профиль врача или клиники (подписка), не с пациента. Это соответствует модели Zocdoc и Psychology Today, где платит профессионал.
5. Нужна ли связь врача и пациента для записи. Рекомендация: нет. Запись создает запрос, но не создает `links`. Связь `links` появляется только по приглашению или отдельному согласию, как сейчас.
6. Доступ к карточке при записи. Рекомендация: отдельное действие «поделиться», не автоматически при записи.
7. Срез или живой доступ. Рекомендация: срез на момент согласия по умолчанию. Живой доступ позже, по явной опции пациента с отдельным согласием.
8. Что происходит со старым врачом при переносе. Рекомендация: доступ отзывается автоматически. Сохранить можно только по выбору пациента.
9. Заметки врача. Рекомендация: не переносятся никогда. Пациент получает копию по запросу, если это разрешит юрист.
10. Срок гранта. Рекомендация: до конца приёма плюс 30 дней, дальше продление вручную пациентом.
11. Психиатрические специальности. Рекомендация: отдельное подтверждение доступа для них, в MVP не выделять отдельный режим, а проверить юристом и психиатром.
12. Локализация. Рекомендация: хранить в Казахстане с начала, без исключений. Тестовые данные до заключения юриста. Это решение обязательно до запуска с реальными пациентами.
13. Экстренные случаи. Рекомендация: запись не используется для срочной помощи, текст об этом показывается при записи (как в `KAZAKHSTAN.md`).
14. Порядок работ. Рекомендация: сначала закрыть пункты из `GAP-CLOSURE.md` (восстановление доступа, экспорт и удаление аккаунта, проверенные резервные копии), потом запись и карточку.
15. Допуск врачей. Рекомендация: записываться только к врачам с `specialist_verified_at`. Врач без подтверждения в каталоге не появляется.
