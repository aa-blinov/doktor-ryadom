# UI врача: экраны, роли и целевые действия

> Оценка по коду, не проверено в браузере.

Описаны экраны кабинета врача (React + Mantine, маршруты hash-based). Источники: `app/src/App.tsx`, `app/src/Doctor.tsx` и связанные компоненты; API в `app/server/index.ts`, `care.ts`, `surveys.ts`.

Всего 13 экранов. Отдельных маршрутов для «опросов», «приглашения» и «напоминаний» нет: это модалка или блоки внутри экранов выше.

Не описаны как врачебные экраны: вход и восстановление доступа (общие для ролей, `App.tsx`), PWA-установка, модалка обучения `Onboarding.tsx` (открывается при первом входе и кнопкой «Как пользоваться Рядом» в `#/settings`).

Вкладки карточки пациента не меняют hash: состояние вкладки хранится в React и `sessionStorage` (`ryadom-section:<врач>:<пациент>`). Поэтому при повторном открытии пациента может открыться не «Обзор», а последняя вкладка этой сессии.

## Навигация и роли
- После входа врач попадает на `#/patients`. Боковое и нижнее меню врача: «Пациенты», «Аккаунт».
- Корень без hash открывает `#/today`. Список показывается, но пункт «Пациенты» не подсвечен (`App.tsx`, поле `current`).
- Кабинет врача показывает пациентов только по активной связи. Все `/api/doctor/patients/:id/*` проверяют `links` и возвращают 403 после отзыва доступа (`index.ts`).

## Гейт верификации (`specialist_verified_at`)
Гейт ограничивает функции, а не весь кабинет.
- `POST /api/doctor/invites` без верификации возвращает 403 («Подтвердите профиль специалиста…»). UI показывает текст ошибки над списком, модалка не открывается.
- `GET /api/doctor/code` отдаёт `active`. Пока `false`, код есть, но пациенты по нему не подключаются (`DoctorCode.tsx`).
- `GET /api/invites/:token` и `POST /api/patient/accept` требуют верификацию врача. Пациент не подключится по приглашению неверифицированного врача.
- Верификацию ставит только скрипт `scripts/verify-specialist.mjs`, в UI этого нет.
- Смена ФИО или специальности сбрасывает верификацию (`profiles.ts`, `recheck`). UI предупреждает в `ProfileSettings.tsx`.

## Целевые действия: что значит «готово»

| # | Действие | Готово, если | Статус по коду |
|---|---|---|---|
| a | Видеть пациентов, требующих внимания | Фильтр «Требуют внимания» оставляет только пациентов с флагом (SOS, PHQ-9 п.9, нет отметок ≥3 дней, самочувствие ≤2) | Готово |
| b | Открыть пациента с новым SOS | Карточка открыта, сервер пометил `sos_events.acknowledged_at`, бейдж пропал из списка | Готово; SOS в самой карточке не показан |
| c | Просмотреть флаг PHQ-9 пункт 9 | Нажата «Подтвердить просмотр результата» (`reviewed_at` заполнен) | Готово; ссылка из Обзора ведёт на вкладку «План», а не «История» |
| d | Просмотреть практику пациента | «Подтвердить просмотр отзыва»: `reviewer_id` = текущий врач | Готово |
| e | Подтвердить просмотр отметки цели | Есть кнопка, вызывающая `POST .../goal-logs/:id/review` | Не реализовано: эндпоинт есть, вызова из UI нет |
| g | Изменить план наблюдения | `PUT .../plan` сохранён («План сохранён»); рекомендации добавлены в «Записи приёма» | Готово |
| h | Отправить опрос пациенту | Назначен стандартный опросник (`POST .../assessments`) или свой (`POST .../surveys`) | Готово; назначенный свой опрос в UI врача не виден |
| i | Создать приглашение новому пациенту | Показана одноразовая ссылка (`POST /api/doctor/invites`), её можно скопировать | Готово при верификации врача |
| j | Найти последнюю отметку пациента | Дата и самочувствие последней отметки видны | Готово, 0 кликов в списке |

Подробные пути и число кликов: [clicks.md](clicks.md).

## Изменения (после первичной карты)

- Вкладки карточки сведены к четырём: «Обзор» (полоса «Состояние сейчас» и блок «Перед приёмом»), «Цели», «История», «План наблюдения». «К приёму» удалена, «Записи приёма» перенесены в «План наблюдения».
- Экран сводки у пациента удалён, кнопка «К приёму» в истории тоже.
- Старые значения вкладки из `sessionStorage` («report», «treatment») открываются как «Обзор».
