# Администратор: экран против данных

_13 октября 2026 · проверено 11 кейсов в Chrome, 320 и 1440 px, обе темы_

Независимая проверка роли администратора. Для каждого действия сравнивались три источника: что администратор видит на экране, что вернул API и что реально лежит в SQLite (`app/tests/db-adapter.ts`, база в памяти). Экран снимался в реальном Chrome через Playwright поверх живой сборки `app/dist/client`; запросы браузера перехватывались и уходили в тот же Hono-сервер, что и API-замеры.

Схема замера: администратор заведён регистрацией с ролью `doctor`, затем повышением в БД через `.prepare(...).bind(id).run()` с обязательной проверкой `SELECT role FROM users WHERE id=?` — во всех прогонах роль подтверждена как `admin`. Ни один файл в `app/` и `docs/` не менялся, git не трогался. Скриншоты и сырые замеры: `/tmp/qa2-admin/`.

## Дефекты

### 1. «Отменить» снимает блокировку с чужого аккаунта — критично

Затрагивает и «Врачей», и «Пациентов». Кнопка «Отменить» в баннере не помнит, кого только что заблокировали: она ищет первый в списке аккаунт с `blocked_at` (`app/src/AdminArea.tsx:34` и `app/src/AdminArea.tsx:56`, `patients.find(x=>x.blocked_at)?.id`).

**Врачи.** Заблокированы по очереди Тимур → Улан → Ерлан. Перед последним кликом баннер писал: «Врач **Ерлан Подтверждённый** заблокирован. Это было сделано только что.» После «Отменить»:
- экран: баннер исчез, список перезагружен;
- API: `POST /admin/accounts/<id>/block {blocked:false}` ушёл на **Тимура**;
- база: `Тимур Подтверждённый.blocked_at = NULL`, а `Ерлан Подтверждённый.blocked_at` и `Улан Подтверждённый.blocked_at` остались заполнены.

Журнал подтверждает расхождение собственными записями: `block_account · Ерлан Подтверждённый`, затем `unblock_account · Тимур Подтверждённый`.

**Пациенты.** Тот же сценарий: заблокированы Александр Новейший («Пациент 1»), Зоя Средняя («Пациент 2»), Глеб Первосозданный («Пациент 3»). Баннер: «Пациент **№1** заблокирован. Это было сделано только что.» После «Отменить» в базе `Александр Новейший.blocked_at = NULL`, а Зоя и Глеб остались заблокированы. Для администратора это выглядит как «отмена сработала», хотя снят совсем другой аккаунт, а два других остались заблокированы без всякого уведомления.

### 2. Подтверждение блокировки пациента называет перевёрнутый номер — критично

Заголовок карточки — «Пациент N» по позиции в списке, а диалог подтверждения и баннер считают номер как `patients.length - patients.indexOf(p)` (`app/src/AdminArea.tsx:51`). При трёх пациентах:

| Карточка на экране | Кто в базе | Диалог подтверждения |
|---|---|---|
| Пациент 1 | Александр Новейший | «Заблокировать пациента **№3**?» |
| Пациент 2 | Зоя Средняя | «Заблокировать пациента **№2**?» |
| Пациент 3 | Глеб Первосозданный | «Заблокировать пациента **№1**?» |

Нумерация зеркальная. Администратор подтверждает блокировку «пациента №1», а система блокирует «Пациент 3». Средний пункт совпадает случайно, поэтому при беглом просмотре дефект незаметен. Положение усугубляется тем, что все три аккаунта созданы в один день — экран показывает «Аккаунт создан 13 окт.» для всех, и сверить номер с датой невозможно.

Отдельно: текст диалога «Действие обратимо только вручную в списке» противоречит баннеру с «Отменить», который появляется сразу под ним.

### 3. Журнал приписывает действия пациентов «Системе» — существенно

Сервер отдаёт `actor_role` по-русски — `'пациент'`, а интерфейс сравнивает с английским `'patient'` (`app/src/AdminArea.tsx:78`). Замер на экране:

> Вход в аккаунт · пациент — 13.10.2026, 11:36:43 · **Система (пациент)**
> Отзыв о враче · Тимур Первый — · **Система (пациент)**
> Пациент подключился · Тимур Первый — · **Система (пациент)**

API отдаёт для этих же строк `actor_name: null, actor_role: "пациент"`, а в базе `actor_id` указывает на конкретного пациента. То есть экран утверждает, что действие выполнила система, тогда как API и база называют пациента. Для журнала, который администратор читает как «Кто и что сделал в портале», это прямое искажение. Затронуты все пациентские события: вход, отметка, отзыв, подключение.

### 4. «Решение по заявке» не различает три решения и не называет врача — средне

В журнале подтверждение, запрос уточнения и отказ попадают под одну подпись «Решение по заявке» без указания врача. Замер: подряд идут четыре записи «Решение по заявке» по четырём разным врачам, и различить их нечем — `subject_id` указывает на id заявки, а не на пользователя, поэтому `subject_name` всегда `NULL`. При этом соседняя запись «Врач подал заявку · Ерлан Подтверждённый» врача называет. В базе `specialist_requests.status` различает `approved`, `needs_info` и `rejected` — информация есть, но до журнала не доходит. Тем же свойством обладают «Отзыв скрыт» и «Приглашение создано»: субъект не подписан.

### 5. Подтверждённый врач без типа пропадает из всех фильтров каталога — низко

Если в «Врачах» выбрать «Не указан» у уже подтверждённого врача, `specialty_kind` обнуляется, но `specialist_verified_at` остаётся, и `specialist_requests.kind` у уже решённой approved-заявки тоже обнуляется. Замер: до смены фильтр `?kind=psychologist` возвращает врача, после — 0; при этом врач остаётся в общем списке каталога и в `/api/me` у него `specialist_verified_at` задан, `specialty_kind: null`. Экран «Врачей» при этом показывает «Подтверждён» рядом с «Тип не указан» — противоречие видно, но причину сервер не объясняет. Тип снимается без подтверждения и попадает в аудит как обычное «Тип специалиста изменён».

## Не удалось проверить

- **Письма врачу о решении по заявке.** Ветка отправки требует `MAIL` в окружении и `email_verified_at` у врача; в тестовой базе почты не подтверждены, письмо не уходило.
- **Экран врача сразу после одобрения без перезагрузки.** На уровне API подтверждение действует мгновенно (приглашение создаётся по старой сессии, 201). Меню врача строится из состояния, загруженного при входе, поэтому пункт «Пациенты» появляется только после перезагрузки — экран врача в этой части проверен косвенно, по тексту подсказки «Если пациентов не видно, обновите страницу».
- **Фильтр «Тип события» и пагинация «Показать ещё» в журнале.** Не измерялись.
- **Поведение на больших списках.** API режет выдачу `LIMIT 300` (врачи, пациенты) и `LIMIT 200` (заявки, отзывы); на реальном объёме не проверялось, что интерфейс сообщает об обрезке.
- **Push-уведомления и service worker** — в тестовом окружении заблокированы, на замеры не влияли.

## Проверенные кейсы

**К1. Заявки врачей: список, заявка с типом и заявка без типа.** В прогонах участвовало до восьми врачей, подавших заявки; на экране администратора карточки выстроены в порядке «на проверке → нужны уточнения → решённые», внутри групп — от новых к старым (в замере с пятью врачами — 5 карточек, порядок совпал с порядком в базе). Заявка без типа получена единственным доступным способом — администратор снял тип в разделе «Врачи» (`POST /admin/doctors/:id/kind {kind:null}` → 200, `specialist_requests.kind` стал `NULL`). Форма врача требует выбор типа (`required` на `select`), через API пустую заявку создать нельзя — 400. На экране кнопка «Подтвердить» неактивна, подсказка объясняет причину и указывает верный раздел; прямой обход кнопки через API даёт 400 с тем же условием. Расхождений нет.

**К2. Решение по заявке: подтверждение, запрос уточнения, отказ.** Подтверждение записало `specialist_requests.status='approved'`, `reviewer_id` администратора, комментарий врачу, а также `users.specialist_verified_at` и `users.specialty_kind`. Уточнение и отказ записали `needs_info`/`rejected` с обязательным комментарием (без комментария сервер отвечает 400), `specialist_verified_at` остался `NULL`. Повторное решение по решённой заявке — 409. Врач видит ровно то, что в базе: `verified:false`, `status`, `admin_note`. Расхождений нет.

**К3. Приглашения и пациент после решения.** Подтверждённый врач создал приглашение (201, токен выдан) и увидел пустой список пациентов до подключения. Врач с `needs_info` и врач с отказом получили 403 «Подтвердите профиль специалиста у администратора, чтобы приглашать пациентов». После принятия приглашения пациентом появилась строка `links`, и врач увидел пациента. Расхождений нет.

**К4. Смена типа специальности в разделе «Врачи».** Смена `psychologist → psychiatrist` синхронно обновила `users.specialty_kind`, `specialist_requests.kind` (в том числе у уже решённой approved-заявки), карточку публичного каталога и пилюлю на экране. Попытка сменить тип у пациента отклонена (400). Статус врача не меняется — `specialist_verified_at` не трогается. Единственное найденное расхождение — дефект 5 (обнуление типа у подтверждённого врача).

**К5. Врачи: поиск, блокировка, разблокировка.** Поиск работает по имени и по почте, пустой запрос не ломает выдачу. Блокировка удаляет все сессии врача (`count(*)=0`), старый cookie даёт 401, новый вход — 403 «Аккаунт заблокирован. Обратитесь к администратору», врач исчезает из публичного каталога. В браузере заблокированный врач выбрасывается на экран входа без утечки данных. Блокировка собственного аккаунта администратора запрещена (403), повторная блокировка и повторная разблокировка идемпотентны. Расхождение — дефект 1.

**К6. Пациенты: блокировка, разблокировка, отмена.** `GET /admin/patients` отдаёт только `id`, `created_at`, `blocked_at` — ни имён, ни почт. Блокировка пациента работает так же, как врача: сессии удаляются, вход 403, старый cookie 401. Ручная разблокировка кнопкой «Разблокировать» снимает блокировку с нужного аккаунта. Ошибки в двух местах — дефекты 1 и 2.

**К7. Отзывы: скрытие и возврат.** «Скрыть отзыв» пишет `hidden_at`, карточка переключается на «Скрыт», в публичном каталоге у врача пропадают и отзыв, и рейтинг (`rating:null`, `reviewCount:0`). «Вернуть отзыв» возвращает всё на место (`rating:5`, `reviewCount:1`). Скрытие несуществующего отзыва — 404. Автор в админском списке показан псевдонимом «Пациент N», реальные имя и почта не передаются. Расхождений нет.

**К8. Журнал действий.** 43 записи в базе, 43 в API — состав совпадает полностью. Каждая административная операция пишет запись: решение по заявке, смена типа, блокировка и разблокировка, скрытие и возврат отзыва. Подписи администратора и врача корректны («Админ Кузьмин (администратор)», «Тимур Первый (врач)»). Два расхождения — дефекты 3 и 4.

**К9. Границы доступа.** Все пять разделов `/api/admin/*` закрыты для пациента и для врача (403), для анонимного — 401. Прямые попытки выполнить административное действие чужой ролью (решение по заявке, блокировка, смена типа, скрытие отзыва) дают 403 и не оставляют следов в базе. В браузере пациент, открывший `#/admin`, получает свой личный кабинет, врач — «Подключение врача»; административных экранов и данных в DOM нет. В каталог врач не попадает (403), оставлять отзывы тоже не может.

**К10. Обещания интерфейса против сервера.** Проверены подписи на всех пяти административных экранах. «Блокировка закрывает вход и завершает сессии» — соответствует серверу. «Имена и почты пациентов администратору не показываются. Видны только даты и статус аккаунта» — соответствует выборке в SQL. «Отзывы публикуются сразу. Скрытый отзыв пропадает из каталога и из рейтинга» — соответствует. «Кто и что сделал в портале» — не соответствует для пациентских действий, см. дефект 3.

**К11. Оформление.** Все пять административных экранов сняты в светлой и тёмной темах на 1440 и 320 px (19 скриншотов в `/tmp/qa2-admin/shots/`). Горизонтальной прокрутки нет ни на одной ширине, ошибок JavaScript в консоли — 0. Баннер установки PWA перекрывает верхнюю панель на 320 px — это известное ограничение тестового окружения, перед замерами он скрывался.
