# Пациент: экран против данных

_13 октября 2026 · проверено 11 кейсов в Chrome 150, 320 и 1440 px, светлая и тёмная темы_

Метод: для каждого действия сравнивались три источника — (1) текст и значения на экране,
(2) ответ `GET /api/patient/data` и прочих API, (3) прямые `SELECT` по SQLite (`node:sqlite`,
обёртка `app/tests/db-adapter.ts`). Все прямые записи в БД выполнялись только через
`.prepare(sql).bind(...значения).run()` — вызов `.run(id)` без `.bind()` в этой обёртке молча
ничего не делает, поэтому такой способ не использовался. Окружение поднималось на
`app/dist/client` после `npm run build`, API — через `app.request`, файлы — из `dist/client`,
service worker заблокирован, баннер `.pwa-notice` скрывался через CSS. Скриншоты и логи —
в `/tmp/qa2-patient/`. Файлы проекта не изменялись.

## Дефекты

### 1. Последний вопрос отметки («Заметка врачу») недостижим обычным кликом — отметка сохраняется досрочно

**Серьёзность: высокая.** Ломается основной сценарий и теряются данные.

**Как воспроизвести.** Войти пациентом с подключённым врачом и планом из 6 вопросов
(`sleep/anxiety/energy/functioning = true`). Пройти вопросы 1–5, на шаге «Сон и действие»
выбрать сон и отметку действия, затем нажать «Дальше» обычным кликом мыши.

**Ожидалось.** Открывается шестой вопрос «Заметка врачу», пациент пишет текст и сам
нажимает «Сохранить отметку».

**Получилось.** Вместо шестого вопроса сразу открывается экран «Отметка сохранена»
(маршрут `#/saved`), а в БЗ записывается отметка с **пустой заметкой**.

Трассировка событий в браузере:

```
click:button|Дальше
SUBMIT:submit|Сохранить отметку
hash: #/saved
база: checkins -> {mood:4, sleep:5, anxiety:1, energy:4, functioning:2, note:'', habit:1}
```

**Область воспроизведения.** Замерено и на плане врача из 6 вопросов, и на плане по умолчанию
из 5; на ширинах 1440 и 320 px; и мышью (нажатие 80–120 мс — обычная длительность), и с
клавиатуры (Tab + Enter). При мгновенном синтетическом клике (`delay: 0`) кнопка, наоборот,
не срабатывает вовсе — шаг тоже не открывается. Рабочий обход есть только один:
программный вызов `dispatchEvent('click')`; обычный путь «Назад» → «Дальше» работает, потому
что не ведёт на последний шаг.

**Почему.** В `app/src/Patient.tsx:177` кнопка перехода — `type="button"` с
`onClick={() => setStep(step+1)}`, а на последнем шаге она заменяется кнопкой
`type="submit"` (`Patient.tsx:176`). React перерисовывает кнопку прямо во время обработки
клика, и браузер применяет действие активации уже к новой `submit`-кнопке, что и отправляет
форму. Дополнительно `Patient.tsx:89` ограничивает восстановление шага из черновика
значением `Math.min(step, 4)`, поэтому вернуться на последний шаг из черновика нельзя.

### 2. Быстрый путь молча записывает 8 часов сна, которых пациент не указывал

**Серьёзность: высокая.** В дневник попадает клиническое значение, выдуманное интерфейсом.

**Как воспроизвести.** Пациент с планом, где `sleep = true`, открывает «Отметка за сегодня»,
выбирает только настроение и нажимает «Сохранить и пропустить остающееся».

**Ожидалось.** В `checkins` записывается то, что пациент реально ввёл; сон остаётся пустым
(`null`), раз он не задан.

**Получилось.**

```
экран: вопросов задано 1 из 6, сон не спрашивали
API:   entries[0].sleep = 8
база:  checkins.sleep = 8, habit = null
```

В истории эта запись потом выглядит как достоверные «8 ч сна».

**Почему.** `app/src/Patient.tsx:88` инициализирует форму как
`{sleep: plan.sleep ? 8 : null, …}` — значение 8 ч подставляется заранее и уходит в БЗ вместе
с остальной формой, минуя вопрос.

### 3. Привычка и порядок просмотра записей, заданные врачом, пациенту не показываются

**Серьёзность: средняя.** Обещание врачебной формы не выполняется.

**Как воспроизвести.** Врач в «Плане наблюдения» заполняет «Привычка пациента» и «Порядок
просмотра записей» и сохраняет план. Пациент открывает «План врача», «Настройки», «Сегодня»,
«Цели».

**Ожидалось.** Врачебная форма прямо говорит: «Пациент увидит это в своих настройках»
(`app/src/Doctor.tsx:89`) и «Пациент прочитает его в своих настройках» (`Doctor.tsx:90`).

**Получилось.**

```
экран «План врача»:  habit найден — false,  reviewNote найден — false
экран «Настройки»:   habit найден — false,  reviewNote найден — false
API: plan.habit      = "Дыхание 4-6 после пробуждения"
API: plan.reviewNote = "Врач смотрит записи по вторникам и отвечает до среды"
база: plans.data     = оба текста сохранены
```

Те же два поля нигде не рендерятся в `app/src`: поиск по `plan.habit` и `plan.reviewNote` в
`app/src/*.tsx` даёт только `Doctor.tsx` и несвязанный `assessment.safety.reviewNote` в
`Care.tsx`. Не показывается и `plan.frequency` — частота влияет только на фоновые напоминания.

### 4. Офлайн приложение скрывает и SOS, и номер 112

**Серьёзность: средняя (безопасность пациента).**

**Как воспроизвести.** Открыть приложение без сети (`navigator.onLine === false`) и зайти на
`#/sos` или `#/today`.

**Ожидалось.** Хотя бы возможность позвонить 112 и понятное объяснение, что сигнал не уйдёт.

**Получилось.** Всё приложение заменяется одним экраном:

```
рядом.
Нет подключения к интернету
Для входа и загрузки записей нужно соединение
Попробовать снова
```

Кнопки «Мне сейчас плохо» на экране нет, ссылки на 112 нет, `sos_events` не меняется.
Собственная обработка офлайна у SOS-кнопки («Нет подключения к интернету. Сигнал не
отправлен.» + «Позвонить 112», `app/src/Patient.tsx:81`) недостижима: `app/src/App.tsx:29`
рендерит заглушку раньше, при `!user && !online`, а `user` при старой офлайн-сессии не
загружается (`App.tsx:25`).

### 5. Экран обещает доставку SOS по почте и в уведомления, доставку запускает не всякий запуск

**Серьёзность: средняя.** Заявлено как сверхважное, а механизм запуска не универсален.

**Как воспроизвести.** Прочитать код доставки и конфигурацию развёртывания.

**Ожидалось.** Фоновый процесс, который разошлёт сигнал врачу, есть везде, где работает API.

**Получилось.** Запись создаётся (`POST /patient/sos` → `sos_events`, `audit: sos_alert`), но
`notified_at` остаётся `null` — заполняет его только `deliverNotifications`
(`app/server/jobs.ts:29–40`). Он запускается исключительно из `app/server/node.ts:14`
(`setInterval(jobs, 60000)` — self-hosted/docker-сборка). В worker-сборке
`app/server/index.ts:185` экспортирует только Hono-приложение, обработчика `scheduled` нет,
а в `app/wrangler.jsonc` отсутствует `triggers.crons`. Дополнительно письмо отправляется
только при `email_verified_at` врача и настроенном `MAIL` (`jobs.ts:11`, `jobs.ts:37`).

Фактическую доставку в этом окружении проверить нельзя — см. «Не удалось проверить».

### 6. Счётчик «Заполнено N из 2» не считает «Небольшое действие»

**Серьёзность: низкая.** Вводит в заблуждение, данные не портит.

**Как воспроизвести.** План с `sleep = true`. На шаге «Сон и действие» выбрать и сон,
и «Получилось».

**Ожидалось.** «Заполнено 2 из 2».

**Получилось.** «Заполнено 1 из 2». На следующем шаге с пустой заметкой — тоже «Заполнено 1
из 2».

**Почему.** `app/src/Patient.tsx:100` считает `[plan.sleep && entry.sleep !== null,
entry.note.trim().length > 0]`, а `detailsTotal` (строка 101) — `plan.sleep ? 1 + 1`.
Отметка «Небольшое действие» (`entry.habit`) в расчёт не входит вовсе.

### 7. После подключения врача остаётся фраза «Пока врач не подключён, записи видны только вам»

**Серьёзность: низкая.** Текст противоречит соседнему блоку.

**Ожидалось.** Либо фраза исчезает, либо меняется.

**Получилось.** В блоке «Доступ к записям» одновременно показаны «Абат Врачебный / Имеет доступ
к вашей истории» и «Пока врач не подключён, записи видны только вам» — абзац выводится
независимо от ветки подключения (`app/src/Patient.tsx:192`).

### 8. Состояние «сигнал отправлен» не восстанавливается в новой вкладке

**Серьёзность: низкая.** Дубликатов в БЗ нет, но экран расходится с данными.

**Как воспроизвести.** Отправить SOS, затем открыть `#/sos` в другой вкладке того же
браузера.

**Ожидалось.** Состояние «Сигнал отправлен … 11:47».

**Получилось.** Снова кнопка «Мне сейчас плохо», хотя в `sos_events` строка есть.
Метка лежит только в `sessionStorage` с TTL 30 минут (`app/src/Patient.tsx:69–70`), сервер
дедуплицирует повтор только в пределах 60 секунд (`app/server/index.ts:105`). В той же
вкладке после перезагрузки состояние сохраняется корректно.

## Не удалось проверить

- **Фактическая доставка SOS и напоминаний** (письмо, push, `notified_at`). В тестовом
  окружении фоновый `deliverNotifications` не запускается — он поднимается только
  `server/node.ts`; `MAIL` и `PUSH_PUBLIC_KEY` не заданы. Замер ограничен тем, что строка в
  `sos_events` создаётся, а `notified_at` остаётся `null`.
- **Блок уведомлений на устройстве и переключатель «Напоминать по email»** в настройках.
  В `ReminderSettings.tsx:16` они рендерятся только при `cap.email` / `cap.publicKey`, которых
  в тестовом окружении нет: на экране вместо них ничего не появляется. Косвенно проверено
  только, что `PUT /settings` с `reminderEmail: true` при неподтверждённом адресе честно
  возвращает `false`.
- **Реальное офлайн-поведение service worker'а**: в тестовом окружении SW заблокирован,
  поэтому офлайн имитировался флагом `navigator.onLine`, а не обрывом сети.
- **Конфликт правки отметки** (расхождение `expectedVersion` между двумя вкладками) —
  сценарий не гонялся.
- **Доступность с клавиатуры** проверялась только в части кнопки SOS; системного аудита
  фокус-порядка не было.

## Проверенные кейсы

1. Регистрация пациента: обязательность согласия, запись `registration_consent` в `audit`.
2. Онбординг: пропуск (4 клика) и полный проход (4 экрана), отметка в `localStorage`,
   отсутствие следа в БД, повторное открытие.
3. Отметка состояния: полный путь из 6 вопросов по плану врача с проверкой сна, тревоги,
   энергии, обычных дел, «После короткого сна», отметки действия и заметки; быстрый путь
