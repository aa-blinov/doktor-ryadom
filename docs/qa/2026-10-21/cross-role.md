## 4. Дефекты

### X-01 — Невалидный JSON возвращает 503 вместо 400 (minor)

* **Кейс:** 11.5 (плюс 8.x — `POST /api/admin/accounts/:id/block` с пустым телом).
* **Воспроизведение:**
  ```bash
  curl -s -i -X POST http://127.0.0.1:8794/api/patient/checkins \
    -H 'Origin: http://127.0.0.1:8794' -H 'Content-Type: application/json' \
    -H 'Cookie: <ryadom_session пациента>' \
    --data-binary '{"date": "2026-10-21", "mood":'
  ```
  Фактически: `HTTP/1.1 503` `{"error":"Не удалось выполнить запрос. Данные формы сохранены на экране; попробуйте ещё раз."}`.
  Ожидается по контракту ошибок (GUIDE.md, п. «Коды»): `400` — «невалидные данные».
  Тот же ответ дают `POST /api/patient/goals` с телом `не json` и `POST /api/admin/accounts/:id/block` с пустым телом.
* **Ожидаемое:** 400 с сообщением о неверных данных (клиент не должен показывать «данные формы сохранены» при мусорном запросе).
* **Фактическое:** 503 — общий обработчик ошибки.
* **Вероятная причина:** `await c.req.json()` вызывается без `try/catch` в обработчиках; `SyntaxError` уходит в `app.onError` (`app/server/index.ts:46`), который всегда отдаёт 503. Затронуто **53 места** в `app/server/*.ts`, например `app/server/index.ts:66` (`/auth/register`), `:76` (`/auth/login`), `:133` (`/patient/checkins`), `app/server/care.ts:18,24,38,45,57,68,76`, `app/server/admin.ts:30,48`, `app/server/card.ts:67,81`, `app/server/booking.ts:55,82,132`, `app/server/account.ts:29,37,47,60,73,79,88,97,105,142`.
* **Предложение (без правки кода):** обернуть разбор тела в общий помощник, который при `SyntaxError` отвечает 400 «Проверьте формат запроса», и вызывать его вместо голого `c.req.json()`; `onError` оставить только для неожиданных сбоев.

### X-02 — Приглашение от заблокированного врача принимается пациентом (major)

* **Кейс:** 8.9, 8.10, 8.16.
* **Воспроизведение:**
  1. Врач D1 (верифицирован) создаёт приглашение: `POST /api/doctor/invites` → 201, `token=bab09d77e8f58849dd441e0a6e05e5a37d157d1274c350b806fed11580b9abe9`.
  2. Админ блокирует врача: `POST /api/admin/accounts/9951646c-1699-4f39-8a39-80cab2f35e73/block` `{"blocked":true}` → 200.
  3. Предпросмотр: `GET /api/invites/bab09d77…` → **200** `{"doctorName":"QA Врач Основной","doctorProfile":{"timezone":"Asia/Almaty","visitFormat":"both",…}}` — ожидается 404.
  4. Пациент отзывает прежнего врача и принимает это приглашение: `POST /api/patient/accept {"token":"bab09d77…","consent":true}` → **200 `{"ok":true}`** — ожидается 404/403.
  5. После этого `GET /api/patient/data` у пациента показывает `doctor.id=9951646c…` (подключение к заблокированному врачу), а врач не может открыть данные: `GET /api/doctor/patients/<id>/data` → 403 «Аккаунт заблокирован…».
* **Ожидаемое:** заблокированный врач исключается из всех точек входа пациента (как уже сделано в каталоге и записи на приём), пациент не подключается к врачу, который не сможет читать его данные.
* **Фактическое:** пациент успешно подключается к заблокированному врачу; данные пациента уходят «в никуда» без предупреждения.
* **Вероятная причина:** SQL выборок приглашений проверяет `specialist_verified_at`, но не `blocked_at`: `app/server/index.ts:52` (предпросмотр приглашения) и `app/server/index.ts:176` (`source` для accept). Для сравнения, в `app/server/directory.ts:14` и `app/server/booking.ts:15` используется условие `VERIFIED_DOCTOR` с `u.blocked_at IS NULL` — то есть правило в проекте есть, но не применено к приглашениям.
* **Предложение:** переиспользовать единое условие «верифицирован и не заблокирован» в `index.ts:52` и `index.ts:176`; дополнительно гасить (`used=1`) все выданные, но неиспользованные приглашения врача при блокировке аккаунта.

### X-03 — Выгрузка врача фактически пуста (minor)

* **Воспроизведение:**

  ```bash
  curl -s http://127.0.0.1:8794/api/account/export -H 'Cookie: <ryadom_session врача>'
  ```
  Фактически в `data` 22 таблицы, из них непустые только `settings=1`, `notices=5`; `checkins=0`, `followups=0`, `reports=0`, `card_entries=0`, `practices=0`, `goals=0`.
  Врач создал авторскую практику: `POST /api/doctor/practices` → 201 «QA-практика врача», `GET /api/doctor/practices` → 1 шт., но таблицы `practice_templates` в выгрузке **нет вовсе**.
* **Ожидаемое:** выгрузка врача содержит его рабочие данные (авторские практики, приглашения, связи с пациентами, сведения о пациентах, к которым есть доступ).
* **Фактическое:** выгрузка содержит только настройки и уведомления.
* **Вероятная причина:** `EXPORT_TABLES` (`app/server/account.ts:113`) не содержит `practice_templates`, `links`, `invites`, `sos_events`; а `exportJson` (`app/server/account.ts:114-118`) выбирает почти все таблицы по `patient_id=?` — для роли врача это его собственный id, поэтому все таблицы пациентских данных пусты. Ссылка на пациентов (`doctor_id`) не используется вовсе.
* **Предложение:** сделать выборку ролевой: для врача брать строки по `doctor_id`/`links` (его практики, его приглашения, его пациенты и созданные им записи), а `practice_templates` добавить в `EXPORT_TABLES` с выборкой по `doctor_id`; в `README.txt` архива перечислить, что именно выгружено для роли врача.

### X-04 — Выгрузка пациента содержит клинические поля, скрытые в интерфейсе (minor)

* **Кейс:** 10.4.
* **Воспроизведение:**
  ```bash
  curl -s http://127.0.0.1:8794/api/account/export -H 'Cookie: <ryadom_session пациента>'
  ```
  В `data.followups[0].data` ключи: `["notes","goal","nextDate","contact","visitAt","complaints","objective","dynamics","dynamicsNote","diagnosis"]`, значения `QA-диагноз: F41.1`, `QA-жалобы: бессонница`, `QA-объективно: усталость`.
  В `GET /api/patient/data` этих ключей нет (проверено: 5/5 отсутствуют).
* **Ожидаемое:** выгрузка — это «мои данные» из интерфейса; клиническая часть записи врача, которую приложение сознательно не показывает пациенту, либо отсутствует, либо появление её согласовано с продуктом.
* **Фактическое:** выгрузка обходит правило скрытия и отдаёт пациенту диагноз, жалобы и объективный статус из рекомендации.
* **Вероятная причина:** `exportJson` (`app/server/account.ts:114-118`) берёт сырую колонку `followups.data`, тогда как интерфейс применяет фильтр `patientFollowup` (`app/server/index.ts:117`, список полей — `DOCTOR_ONLY_FOLLOWUP_FIELDS` в `app/src/shared.ts:74`).
* **Предложение:** прогнать экспортные строки `followups` через тот же фильтр, что и `/api/patient/data`; если полный архив клинических записей нужен пациенту — вынести это в отдельный явный раздел и задокументировать в `README.txt` архива и в политике выгрузки.

### X-05 — Сигнал SOS не порождает уведомление врачу (major)

* **Кейс:** 9.5 (проверено в 9.1–9.4: сам счётчик `open_sos` работает корректно).
* **Воспроизведение:**
  ```bash
  curl -s -X POST http://127.0.0.1:8794/api/patient/sos -H 'Origin: http://127.0.0.1:8794' -H 'Cookie: <ryadom_session пациента>'
  # → 200 {"ok":true}
  curl -s http://127.0.0.1:8794/api/inbox -H 'Cookie: <ryadom_session врача>'
  # → items: без единого сообщения про SOS
  ```
  Уведомления врача содержат только: «Пациент принял приглашение…», «Пациент отозвал доступ…», «Новая заявка на приём…», «Напоминание о приёме…».
* **Ожидаемое:** сигнал «Мне сейчас плохо» — safety-событие; врач должен узнать о нём сразу (inbox/push), а не только увидев счётчик в списке пациентов при ручном открытии кабинета.
* **Фактическое:** `POST /api/patient/sos` (`app/server/index.ts:140-143`) создаёт запись в `sos_events` и пишет аудит `sos_alert`, но **не вызывает `queueNotice`** — в отличие от всех остальных значимых событий (принятие приглашения, отзыв, запись в карточку, заявка на приём, подтверждение приёма).
* **Предложение:** при создании события `sos_events` добавить `queueNotice(...)` для связанного врача (как в `app/server/index.ts:182` для принятия приглашения), с текстом без диагноза и без имени пациента; продублировать в push. Отдельно решить, должен ли повторный SOS (через минуту) создавать новое уведомление.

### X-06 — Блокировка врача не разрывает подключения пациентов и не уведомляет их (minor)

* **Кейс:** 8.15.
* **Воспроизведение:**
  1. P1 подключён к D1 (связь в `links`, `revoked_at=null`).
  2. `POST /api/admin/accounts/9951646c…/block {"blocked":true}` → 200.
  3. `GET /api/patient/data` пациента → `doctor` по-прежнему `{id:"9951646c…", name:"QA Врач Основной", profile:{…}}`; пациент продолжает отмечать дни и отправлять сводки, но прочитать их не может никто: `GET /api/doctor/patients/<id>/data` → 403 «Аккаунт заблокирован…».
  4. Уведомления пациенту о блокировке врача нет (в inbox пациента только «Врач добавил запись в вашу карточку…», «Врач подтвердил приём…», «Напоминание…»).
* **Ожидаемое:** при блокировке врача его пациенты должны узнать, что ведущего больше нет (и/или связь разрывается с явным сообщением), чтобы не отправлять данные в пустоту.
* **Фактическое:** связь и данные пациента остаются в подвешенном состоянии без объяснений.
* **Вероятная причина:** `POST /api/admin/accounts/:id/block` (`app/server/admin.ts:46-59`) меняет только `users.blocked_at` и не трогает `links`, не ставит `revoked_at` и не создаёт уведомления пациентам (`queueNotice` не вызывается).
* **Предложение:** при блокировке врача помечать его активные связи отозванными (или помечать как «ведущий недоступен») и отправлять пациенту уведомление «Ваш врач временно недоступен, связь приостановлена; ваши данные сохранены». Решение о судьбе данных — сохранять, не удалять.

### X-07 — Аудит отметок пациента не привязан к пациенту (minor)

* **Кейс:** наблюдение в 6.15 (сам дефект не помечен FAIL — это пробел наблюдаемости, а не утечка).
* **Воспроизведение:** `GET /api/admin/audit` содержит строку `{"action":"save_checkin","subject_id":"2026-10-21","actor_name":null,"actor_role":"пациент","subject_name":null,"action_label":"Отметка сохранена"}` — `subject_id` равен дате отметки, а не id пациента; `subject_name` пациентов маскируется в «пациент».
* **Ожидаемое:** администратор может по журналу установить, какой пациент и когда сохранял отметку (без раскрытия содержания отметки).
* **Фактическое:** в журнале видно только, что «кто-то из пациентов» сохранил отметку с датой `2026-10-21`; связать событие с конкретным пациентом нельзя.
* **Вероятная причина:** `logAction(db, id, 'save_checkin', e.date)` (`app/server/index.ts:137`) — субъектом аудита передаётся дата вместо id пациента; дополнительно имена пациентов скрываются условием `CASE WHEN s.role='patient' THEN 'пациент'` (`app/server/admin.ts:65`).
* **Предложение:** передавать в `subject_id` id пациента (а дату — в отдельное поле/контекст события) и добавить админский псевдонимизированный идентификатор пациента (например, `пациент #a1b2`), чтобы администратор мог видеть, что поступило отметок от пациента, не зная его имени.

### X-08 — У врача нет способа создать цель пациенту (minor)

* **Кейс:** 4.7.
* **Воспроизведение:** в `app/server/*` нет маршрута `POST /api/doctor/patients/:id/goals`; цели создаёт только пациент (`POST /api/patient/goals`, `app/server/care.ts:17-22`), врач умеет лишь `POST /api/doctor/patients/:id/goal-logs/:logId/review` (`app/server/care.ts:86-89`).
* **Ожидаемое:** по сценарию задания врач создаёт цель и назначает практику.
* **Фактическое:** назначение практики возможно (через `PUT …/plan`), а создание цели — нет; сценарий проверялся в части «пациент создаёт цель → врач видит → врач отмечает просмотренным», и там всё сходится.
* **Вероятная причина:** функциональность не реализована в объёме роли врача (либо сознательное решение продукта, не отражённое в сценарии).
* **Предложение:** решить на уровне продукта, нужен ли врачу сценарий «поставить цель пациенту»; если да — добавить маршрут создания цели от врача с тем же ограничением «не больше трёх активных целей», что и у пациента.

## 6. Вердикт

**Между ролями система сходится.** Данные, которые записывает пациент, доходят до врача без искажений: 41 из 41
проверенного поля совпали дословно (включая дробный сон 4.5, порядок практик в плане, идентификаторы целей и
логов, таймстемпы «просмотрено», балл PHQ-9), 58 из 60 строк таблицы согласованности совпали. Счётчики
(`count`, `last_date`, `last_mood`, `pending_*`, `open_sos`) совпадают с фактическими данными и корректно
появляются/исчезают по правилам `attentionFlags`. Границы доступа выдержаны: посторонний врач, пациент,
врач и админ получают 403/401 на чужих маршрутах, админ не видит ни клинического текста, ни имён пациентов,
а клинические поля рекомендации не доходят до пациента через `/api/patient/data`. Отзыв доступа и отмена
гонок работают корректно: связь разрывается мгновенно, план удаляется, история остаётся, повторное
подключение без нового согласия невозможно.

**Топ-3 риска:**

1. **X-02 (major) — приглашение заблокированного врача принимается пациентом.** Пациент подключается к
   врачу, который никогда не прочитает его данные; данные продолжают собираться «в никуда» без
   предупреждения. Причина техническая и локальная (не проверяется `blocked_at` в двух SQL выборках),
   но продуктово это ровно тот разрыв, который закрывает весь смысл разграничения ролей.
2. **X-05 (major) — сигнал SOS не доходит до врача в уведомлениях.** Единственный safety-сигнал
   приложения виден врачу только как счётчик в списке пациентов, то есть требует ручного открытия кабинета;
   push/inbox-уведомления по нему нет.
3. **X-06 (minor, но по данным) — блокировка врача оставляет пациентов подключёнными и без предупреждения.**
   В связке с X-02 это даёт сценарий «пациент отправляет данные, их никто не видит, и ни одна сторона
   об этом не знает».

Вне этих трёх — четыре minor (невалидный JSON → 503 вместо 400; пустая выгрузка врача; клинические поля
в выгрузке пациента; аудит отметок без привязки к пациенту) и одно продуктовое наблюдение (нет API создания
цели у врача). Ни один из дефектов не затрагивает числовую согласованность «пациент ↔ врач» и не приводит
к утечке данных между ролями: изоляция пациент/врач/админ в проверенных границах оказалась непроницаемой.

**Рекомендация:** X-02 и X-05 закрыть до пилота (правки локальные, ~2–3 строки в `app/server/index.ts`),
X-06 — вместе с решением по судьбе данных пациентов заблокированного врача; X-01, X-03, X-04, X-07, X-08 —
в бэклог с уточнением продуктовых ожиданий по выгрузке и аудиту.
