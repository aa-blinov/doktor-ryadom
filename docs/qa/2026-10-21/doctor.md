### D-01 — Отзыв о враче публикуется под фамилией пациента, а не под именем

* **Серьёзность:** minor
* **Кейс:** 12.7 (каталог врачей и отзывы)
* **Шаги воспроизведения**

  ```http
  # 1) пациент с именем «Кузнецова Ксения» (регистрация хранит «Фамилия Имя»)
  POST /api/auth/register  {"email":"qa-patd-…@example.com","password":"qa-password-very-long","role":"patient","name":"Кузнецова Ксения","consent":true,"adult":true}
  → 201, cookie ryadom_session

  # 2) пациент оставляет отзыв
  PUT /api/directory/<docA_id>/review   {"rating":5,"body":"Внимательный врач, помог со сном"}
  → 200 {"ok":true}

  # 3) любой другой пациент читает карточку врача
  GET /api/directory/<docA_id>
  → 200 {"reviews":[{"id":"…","rating":5,"body":"Внимательный врач, помог со сном",
                     "author":"Кузнецова",            <-- фамилия
                     "createdAt":…,"hidden":false}], …}
  ```

* **Ожидаемое:** `author:"Ксения"` — отзыв публикуется под именем пациента (PRODUCT.md, раздел 3: «Отзыв: один на пациента на врача, публикуется сразу под именем пациента»; `src/shared.ts:51-56` — `firstNameOf()` по соглашению приложения берёт *имя*, т. е. второй токен, потому что при регистрации хранится «Фамилия Имя»).
* **Фактическое:** `author:"Кузнецова"` — публикуется фамилия.
* **Вероятная причина:** `app/server/directory.ts:12` — `const firstName=(name:string)=>name.trim().split(/\s+/)[0]||'Пациент';` (берёт первый токен = фамилия), используется в `app/server/directory.ts:74` — `author:firstName(r.name)`. Дублирующая логика рядом с `src/shared.ts:52-56` (`firstNameOf`, возвращает `parts[1]`).
* **Предложение (без правки кода):** переиспользовать `firstNameOf` из `src/shared.ts` в `server/directory.ts` и покрыть оба написания имени («Фамилия Имя», одно слово) тестом; в `POST /api/admin/reviews` (строка 99) автор сейчас вообще не показывается — там выводится безымянное «Пациент N».

### D-02 — Второй отзыв того же пациента тому же врачу не отклоняется, а молча перезаписывает опубликованный

* **Серьёзность:** minor
* **Кейс:** 12.8
* **Шаги воспроизведения**

  ```http
  PUT /api/directory/<docA_id>/review  {"rating":5,"body":"Внимательный врач, помог со сном"}
  → 200 {"ok":true}

  # тот же пациент, другой текст и оценка
  PUT /api/directory/<docA_id>/review  {"rating":3,"body":"Передумал, оценка другая"}
  → 200 {"ok":true}          # ожидалось 409

  GET /api/directory/<docA_id>
  → 200 reviews: 1 шт., body="Передумал, оценка другая"   # прежний текст исчез
  ```

* **Ожидаемое:** 409 — «один отзыв на пациента на врача» (заявленное поведение в задании; в БД есть `UNIQUE(doctor_id, patient_id)`).
* **Фактическое:** 200 и обновление существующей строки; опубликованный отзыв переписывается без следа, поэтому скрытая админом копия и любая модерация теряют исходный текст.
* **Вероятная причина:** `app/server/directory.ts:85` — `INSERT … ON CONFLICT(doctor_id,patient_id) DO UPDATE SET rating=excluded.rating, body=excluded.body, updated_at=excluded.updated_at` (upsert). При этом клиент `src/DoctorDirectory.tsx` сознательно предлагает пациенту **редактирование** своего отзыва — то есть поведение «как есть» задумано, а заявленное 409 не совпадает с ним.
* **Предложение (без правки кода):** согласовать контракт: либо ввести 409 на попытку изменить оценку/текст уже опубликованного отзыва (с отдельным маршрутом правки, если он нужен), либо явно зафиксировать в PRODUCT.md, что отзыв редактируемый, а правило «один отзыв на пациента на врача» означает «не более одной записи», и тогда тест-кейс 12.8 должен ожидать 200.

## 4. Непокрытые кейсы

1. **Клиентский UI в браузере не прогонялся** — проверка велась по HTTP API плюс чтение кода `src/Doctor.tsx`, `src/Care.tsx`, `src/DoctorDirectory.tsx`, `src/shared.ts`. Реальные отрисовки форм, модальных окон и мобильной вёрстки врача не проверены; форму назначения препаратов оценено только по коду (10.8).
2. **Отправка уведомлений (SMTP/push) не проверялась** — тестовый стенд без реальной почты; наличие записей в `notices` проверялось, фактическая доставка — нет.
3. **Файлы на границе лимитов** не грузились: фото >5 МБ и видео >50 МБ (413), проверялся только формат и небольшие файлы.
4. **Слоты в чужой часовой зоне** (зона клиники ≠ Asia/Almaty) не проверялись — расчёт `zonedToUtc` проверен только на дефолтной зоне стенда.
5. **Массовые операции** не нагружались: лимит 50 шаблонов опросников (`POST /api/doctor/surveys` → 409), лимит 500 слотов за раз, лимит 300 строк в списке пациентов, `MAX_PENDING_PER_PATIENT=5` заявок без ответа.
6. **Восстановление доступа** (потеря телефона с TOTP, сброс второго фактора администратором, смена пароля, самостоятельное отключение TOTP) вне объёма кейсов врача.
7. **Уведомление врачу о решении по заявке** (`needs_info`/`reject`) не проверялось отдельным кейсом: в API нет маршрута/поля, отдающего такое уведомление, — врач узнаёт о решении только при открытии `GET /api/doctor/verification`.
8. **Клиническая корректность шкал и порогов** (`attentionRules.silentDays=3`, `lowMood=2`, `phq9NeedsReview`) не оценивалась: в `src/shared.ts:39` прямо отмечено, что пороги «не проверены психиатром». Проверено только то, что реализация соответствует заявленным в коде порогам.
9. **Отзыв пациента, не связанного с врачом**, и **отзыв о скрытом админом отзыве** — проверены только основные ветки (12.6, 12.9, 12.13).
10. **Поведение при одновременной работе двух вкладок врача** (гонка версий) проверено только для шаблона опросника (7.11) — для остальных редактируемых сущностей не проверялось.

## 5. Вердикт — топ-3 риска для врача

1. **D-06 (major) — выгрузка врача бесполезна для переноса и для архива.** Врач не может выгрузить данные пациентов, которых ведёт (все клинические таблицы пусты), а архив своей библиотеки практик состоит из картинок и видео без названий и шагов. Для клинической работы это означает, что при смене клиники, при споре о том, что было рекомендовано, или при требовании пациента «выгрузить мои данные» у врача нет корректного ответа — выгрузка есть, а данных в ней нет. Исправить дешевле всего на сервере (расширить `exportJson` для роли врача), и это единственный дефект, который одновременно бьёт по пациенту.
2. **D-03 (minor) — кабинет врача открыт до решения администратора.** Неподтверждённый врач видит список пациентов, библиотеку практик, библиотеку опросников и может создавать практики и опросники, тогда как расписание и приглашения закрыты. Сейчас ущерб ограничен тем, что пациентов у него быть не может, но это единственный путь, на котором врач может начать работать с клиническими материалами без верификации, и расписание — единственный закрытый раздел. При любом расширении функционала (например, «пригласить пациента по коду») этот разрыв станет обходом верификации.
3. **D-01 + D-02 (minor) — отзывы в каталоге показывают фамилию пациента и могут быть молча переписаны.** Пациент «Кузнецова Ксения» публикуется как «Кузнецова» — это и расхождение с заявленным поведением («под именем пациента»), и ненужное раскрытие фамилии в публичном каталоге. Второй отзыв того же пациента не отклоняется, а перезаписывает уже опубликованный, из-за чего скрытая админом копия перестаёт соответствовать тому, что видит каталог. Для врача это риск репутационный: опубликованное мнение пациента может измениться без следа, и врач не увидит об этом уведомления.

**Общий вывод по роли врача:** продуктовая логика врачебного кабинета реализована аккуратно и в целом соответствует заявленному — верификация специалиста, второй фактор с защитой от replay, одноразовые приглашения, границы доступа между врачами/пациентами/админом, право назначать препараты строго у подтверждённого психиатра (и на сервере, и в UI), скрытие клинических полей рекомендаций от пациента, идемпотентность повторных операций — всё это отработало без дефектов (171 PASS из 177 кейсов). Единственный major-дефект (D-06) и три расхождения контракта (D-01…D-03) локализованы и воспроизводимы; правок в код приложения QA не вносил.
