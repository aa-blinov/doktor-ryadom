## 3. Дефекты

### P-01 — серьёзность: **major** — сервер разрешает править запись прошлого дня

- **Кейс:** 2.4 / 2.4b (правка только за сегодня)
- **Шаги воспроизведения:**
  1. `POST /api/patient/checkins` (cookie пациента, `Origin: http://127.0.0.1:8791`)
     `{"date":"2026-10-21","mood":3,"sleep":7,"anxiety":2,"energy":3,"functioning":2,"sleepContext":"usual","note":"QA вчерашняя отметка","habit":false}`
     → `201 {"ok":true}` (запись за вчера создана: id `fa15f4dd-06f9-4fb1-b6fd-23f0d53c1487`, `version` 1)
  2. `GET /api/patient/data` → в `entries` есть запись за `2026-10-21`, `version` 1
  3. `PUT /api/patient/checkins/fa15f4dd-06f9-4fb1-b6fd-23f0d53c1487`
     `{"date":"2026-10-21","mood":5,"sleep":7,"anxiety":2,"energy":3,"functioning":2,"sleepContext":"usual","note":"QA правка вчерашней записи","habit":false,"expectedVersion":1}`
     → **`200 {"ok":true}`**
  4. `GET /api/patient/data` → запись за `2026-10-21`: `mood=5`, `note="QA правка вчерашней записи"`, `version=2`, `updated_at=1792610771231` — то есть в истории видна «Исправлена 21.10.2026»
- **Ожидаемое поведение:** сервер не даёт изменять запись, дата которой не сегодня (продуктовое правило «правка только за сегодня») → `400` с понятным сообщением
- **Фактическое поведение:** `200`, запись прошлого дня перезаписана; исходное значение сохраняется только во внутренней таблице `checkin_revisions` и пациенту/врачу не показывается
- **Вероятная причина:** `app/server/care.ts:44-52` — в обработчике `PUT /api/patient/checkins/:entryId` проверяется только неизменность даты (`app/server/care.ts:48`: `if(existing.date!==e.date) return …400`); ограничения «только сегодня» нет ни на сервере, ни в клиенте — `app/src/History.tsx:22` показывает кнопку «Исправить запись» для любой записи истории
- **Предложение (без правки кода):** зафиксировать решение продукта — либо серверная проверка «дата записи == сегодня» с корректным текстом ошибки, либо явная пометка в UI и `PRODUCT.md`, что прошлые записи переписываются и у врача это видно

### P-02 — серьёзность: **minor** — отметка за будущую дату принимается, текст ошибки вводит в заблуждение

- **Кейс:** 2.9 / 2.9b (дата отметки)
- **Шаги воспроизведения** (чистый аккаунт `qa-patient2-1792610650185@example.com`):
  1. `POST /api/patient/checkins` `{"date":"2026-10-23","mood":3,"sleep":7,"anxiety":2,"energy":3,"functioning":2,"sleepContext":"usual","note":"QA будущая отметка","habit":false}` → **`201 {"ok":true}`** (2026-10-23 — завтра)
  2. `POST /api/patient/checkins` `{"date":"2026-10-21",…}` → `201` (вчерашняя отметка тоже принимается)
  3. `POST /api/patient/checkins` `{"date":"2026-10-24",…}` → `400 {"error":"Можно отметить только текущий день."}`; `{"date":"2026-10-19",…}` → `400` с тем же текстом
  4. `GET /api/patient/data` → в `entries` присутствуют записи с будущей датой `2026-10-23`
- **Ожидаемое поведение:** по тексту собственной ошибки — отметка допустима только за текущий день; отметка за будущее невозможна (самочувствие завтра неизвестно), запись за прошлое — по явному правилу
- **Фактическое поведение:** действует окно «сегодня ±2 дня», будущая отметка создаётся и попадает в данные врача; сообщение об ошибке при этом утверждает «только текущий день»
- **Вероятная причина:** `app/server/index.ts:134` — `if (Math.abs(Date.parse(data.data.date)-Date.now()) > 2*86400000) return c.json({ error:'Можно отметить только текущий день.' },400)` (окно ±2 дня не совпадает с текстом ошибки; в документации API — `/tmp/ryadom-qa/kit/GUIDE.md` — указано «валидные даты: сегодня ±2 дня», то есть продуктовое правило пока не определено)
- **Предложение:** разделить правила для прошедших и будущих дат (будущее — запретить), привести текст ошибки и документацию в соответствие с принятым решением

### P-03 — серьёзность: **minor** — маршрут `GET /api/patient/draft` не реализован

- **Кейс:** 3.3 (черновик)
- **Шаги воспроизведения:**
  1. `PUT /api/patient/draft` `{"entry":{…},"plan":{…},"step":2}` → `200 {"ok":true}` (черновик сохранён)
  2. `GET /api/patient/draft` (та же cookie пациента) → **`404 {"error":"Неизвестный запрос."}`**
  3. `DELETE /api/patient/draft` → `200 {"ok":true}`, `GET /api/patient/data` → `draft: null`
- **Ожидаемое поведение:** маршрут документирован в контракте API (`GET|PUT|DELETE /patient/draft`) и должен отдавать сохранённый черновик → `200`
- **Фактическое поведение:** `404`; работают только `PUT` и `DELETE`. Само приложение не ломается — черновик приходит в `GET /api/patient/data` (`draft`)
- **Вероятная причина:** `app/server/care.ts:37` (`PUT`) и `app/server/care.ts:43` (`DELETE`) — обработчика `GET` нет
- **Предложение:** либо добавить `GET /api/patient/draft`, возвращающий текущий черновик, либо убрать маршрут из документации, чтобы клиенты и интеграции не рассчитывали на него

### P-04 — серьёзность: **minor** (наблюдение, без FAIL-кейса) — повторная отметка приёма препарата молча перезаписывает предыдущую

- **Кейс:** 13.2 (препараты)
- **Шаги воспроизведения:**
  1. `POST /api/patient/medication-logs` `{"medicationId":"46fb19a6-b5c3-4ec9-be3f-5bd1bdd88273","date":"2026-10-22","status":"taken","note":"QA принял"}` → `200 {"ok":true}`
  2. `POST /api/patient/medication-logs` с теми же `medicationId` и `date`, но `status:"missed"` → `200 {"ok":true}`
  3. `GET /api/patient/data` → в `medicationLogs` одна запись: `{date:"2026-10-22", status:"missed"}` — прежний `taken` потерян
- **Ожидаемое поведение:** сохранение истории статусов приёма, иначе врач видит «пропустил», хотя пациент сначала отметил «принял»
- **Фактическое поведение:** upsert — на день и препарат хранится одна запись, прежнее значение перезатирается без предупреждения
- **Вероятная причина:** `app/server/care.ts:71-75` — `INSERT … ON CONFLICT(patient_id, medication_id, date) DO UPDATE`
- **Предложение:** хранить ревизии (как `checkin_revisions` у отметок дня) либо запрещать смену статуса после сохранения и требовать явного подтверждения у пациента

## 4. Непокрытые кейсы

- **Загрузка фото/видео и документы профиля.** Со стороны пациента проверен только запрет: `PUT /api/profile/photo`, `PUT /api/profile/video`, `DELETE /api/profile/video`, `POST /api/profile/documents`, `DELETE /api/profile/documents/:id` → `403` во всех случаях (медиапрофиль — функция врача, `app/server/profiles.ts`, `app/server/upload-limits.ts`). Сама загрузка, лимиты размера (5 МБ фото, 50 МБ видео) и снятие видео в пациентском UI отсутствуют, поэтому с точки зрения пациента не проверялись.
- **CSV-выгрузка.** У пациента CSV-экспорта нет: `GET /api/account/export` отдаёт JSON (`Content-Disposition: attachment; filename="ryadom-data.json"`), CSV есть только в кабинете врача и формируется на клиенте (`app/src/Doctor.tsx`). Формулировка кейса 4 про CSV к пациенту неприменима; проверялись JSON и ZIP (состав и количество строк совпадают с `/api/patient/data`, архив распаковывается, внутри `data.json` + `README.txt`).
- **Доставка напоминаний.** Почта пациента не подтверждена, поэтому `reminderEmail` принудительно возвращается как `false` (кейс 11.6) — фактическая отправка письма/пуша не проверялась.
- **Жизненный цикл аккаунта.** Истечение 7-дневной сессии, восстановление пароля по e-mail, подтверждение e-mail не проверялись (нужны почтовые события и ожидание времени).
- **Гонки при параллельной правке.** Оптимистическая блокировка (`expectedVersion` → `409 «Запись уже изменена в другом окне»`) не воспроизводилась: нужны два одновременных `PUT` одной записи с разными `expectedVersion`.
- **UX-аудит клиента.** Проверка велась по API-контракту; расхождение по P-01 дополнительно подтверждено чтением `app/src/History.tsx:22`. Визуальная проверка экранов пациента не проводилась.
- **Врачебная часть.** Назначение практик, план, опросники и препарат выполнялись в минимальном объёме, необходимом для появления данных у пациента (для назначения препарата врач подтверждён как психиатр).

## 5. Вердикт

**Пациентом пользоваться можно.** Из 105 проверок пройдено 100; дефектов нет ни в одном из базовых сценариев (регистрация/вход/сессия, отметка дня и её границы, черновик, история и выгрузка, практики и блокировки, цели, опросники, SOS, скрытие клинических полей, отзыв доступа врача, настройки, профиль, отметки препаратов, изоляция ролей, устойчивость к повторам, чужому Origin и oversized-телу).

**Топ-3 риска:**

1. **P-01 (major) — переписывание прошлой записи дневника.** Пациент может изменить любую запись прошлых дней; искажается история, которую затем видит врач, а «Исправлена <дата>» не сообщает, что было раньше. Правило «правка только за сегодня» не закреплено ни на сервере (`app/server/care.ts:48`), ни в UI (`app/src/History.tsx:22`).
2. **P-02 (minor) — отметки за будущие дни и противоречивое сообщение об ошибке.** Записи с датой до +2 дней попадают в картину врача, хотя текст ошибки обещает «только текущий день» — пациент и врач получают разное представление о том, что означает отметка.
3. **P-03 (minor) — отсутствует `GET /api/patient/draft` при документированном маршруте.** Любая внешняя интеграция или будущий клиентский сценарий получит `404` вместо черновика (внутри приложения черновик доступен через `/api/patient/data`).
4. *(вне тройки)* **P-04 (minor) — тихая перезапись отметки о приёме препарата:** врач может увидеть «пропустил», хотя пациент ранее отметил «принял».
