### 3.2. Три FAIL, возникшие на стороне проверки (не дефекты приложения)

1. **X-07 (сквозной стенд 8794) — ошибка в моём условии.** Я требовал, чтобы у *всех* событий `save_checkin` субъектом был id P1, но в базе были события ещё и пациента P2 — его `subject_id` законно равен его собственному id. Перепроверено на стенде 8793 с одним пациентом: `subject_id` = id пациента, дат среди субъектов 0 → **PASS**.
2. **«Посторонний врач не видит чужого пациента» и «после отзыва врач теряет доступ» (8794) — 401 вместо 403.** Причина: я разблокировал врача D2 (в рамках A-07), а разблокировка по замыслу **удаляет сессии** (`app/server/admin.ts:62` — `DELETE FROM sessions WHERE user_id=?`), поэтому cookie перестал быть действительным и любой запрос давал 401 «Сеанс завершён». Это заложенное поведение, а не поломка. Обе проверки перепроверены на стенде 8793 с живой сессией: посторонний врач → 403, после отзыва → 403 → **PASS**.
3. **D-05 и вход с верным кодом TOTP (стенд врача, первый прогон) — ошибки в скрипте.** Я брал id практики из `data.id` (в ответе `data.practice.id`) и повторно использовал код, израсходованный включением TOTP. После исправления: удаление неиспользуемой практики → 200, вход с кодом следующего шага → 200.

## 4. Непроверенное

- **X-06 отдельным пунктом** — в исходном `SUMMARY.md` это дубль A-07, проверен совместно.
- **Доставка уведомлений по email и push.** На стендах не настроены `MAIL` и `PUSH_PUBLIC_KEY`, поэтому проверена только постановка уведомления в очередь и его появление во встроенном inbox (`GET /api/inbox`); сам канал отправки не проверялся.
- **Часовые пояса, отличные от `Asia/Almaty` (значение по умолчанию).** Правило «сегодня» считается по часовому поясу пациента из настроек; проверялся только пояс по умолчанию. Границы суток (23:30 по местному времени, «сегодня» по серверу уже другой день) не проверялись.
- **Интерфейс врача и администратора в браузере.** На уровне API проверены библиотека практик, удаление практики, отзывы, заявки, тип специалиста, журнал аудита; в браузере проверялся только интерфейс пациента. Наличие новых кнопок в сборке подтверждено по `dist/client` («Удалить практику», «Убрать отметку», «Исправить можно только сегодняшнюю запись»).
- **ZIP с медиафайлами** (фото/видео профиля, документы, фото и видео практик): проверено только наличие и содержимое `data.json` и `README.txt`; файлы не загружались.
- **Модуль записи на приём (`/doctor/slots`, бронирование)** — проверен только уровень доступа (403 у неподтверждённого врача), сам сценарий бронирования не прогонялся.
- **Нагрузка и гонки** — кроме проверки конфликта версий (409) параллельное редактирование не моделировалось.
- **Возврат в рабочее состояние после блокировки.** По замыслу (см. `FIXES.md`) разблокировка не восстанавливает связь врача и пациента — нужно новое приглашение и новое согласие. Это намеренное продуктовое решение, отдельным сценарием не проверялось.

у врача и админа держит (403/428/401/200, код не переиспользуется), разграничение ролей соблюдается, отзыв доступа рвёт связь
мгновенно и оставляет историю, одна отметка в день и одна отметка приёма на день, практики и цели работают, выгрузка ZIP открывается
и содержит `data.json`, «Отметка за сегодня» в интерфейсе пациента работает. Штатный набор тестов приложения — 104/104.

**Три замечания, которые стоит держать в виду (не регрессии, не дефекты отчёта):**

1. Разблокировка врача **удаляет его сессии** (`app/server/admin.ts:62`) — старый cookie перестаёт работать с 401. Это задумано, но
   в сценариях, где аккаунт разблокируют и продолжают работать с прежней сессией, поведение выглядит как «сеанс завершён».
2. Клиент считает «сегодня» в часовом поясе браузера (`today()` в `app/src/shared.ts:57`), а сервер — в часовом поясе пациента из
   настроек (`app/server/care.ts:140`). Если они разойдутся (переезд, смена пояса в настройках), кнопка «Исправить запись» может
   быть скрыта в день, когда сервер правку разрешает. Сервер остаётся источником истины и отвечает 400 — расхождение только в UI.
3. Смена отметки приёма препарата в интерфейсе неатомарна (`app/src/Care.tsx`: удалить прежнюю, затем создать новую) — если создание
   не пройдёт, прежняя отметка уже удалена. На сервере атомарного «заменить» нет, только запрет перезаписи (409).
