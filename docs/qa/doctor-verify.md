# Врач: экран против данных

_13 октября 2026 · проверено 13 кейсов в Chrome, 320 и 1440 px, обе темы_

Независимая проверка роли «врач»: в каждом кейсе сравнивались три источника — что врач видит
на экране, что вернул API и что лежит в SQLite напрямую. Расхождение любых двух из трёх
считается дефектом.

**Как снимали.** Приложение отдавалось из `dist/client` (`npm run build`), запросы `/api*`
уходили в то же Hono-приложение с SQLite в том же процессе. Экранные действия выполнялись
в Chrome через Playwright вручную: клики, ввод, выборы, скачивание файлов. Данные в базе
читались отдельным запросом через `tests/db-adapter.ts` — **всегда `.prepare(sql).bind(...).run()`**;
при вызове без `.bind()` значения теряются, и такой замер ничего не проверяет.

Отдельно оговорки по окружению:

- service worker в тесте заблокирован, поэтому баннер `.pwa-notice` перекрывал шапку — перед
  кликами он удалялся через `evaluate`;
- на 320 px вкладки карточки скрыты, разделы переключались через выпадающий список `#doctor-section`,
  на 1440 px — через `.doctor-section-tabs button`;
- подтверждение специалиста и блокировка проставлялись прямо в SQL: публичного API для них нет,
  а интерфейс админа проверяет другой проход;
- отметки старше двух дней и часть «сырых» записей (цели, отзывы о практиках) вносились SQL,
  потому что `/patient/checkins` физически ограничен окном ±2 дней, а цели пациент заводит у себя;
- счётчики регистрации (10 минут на IP) чистились между прогонами — троттлинг не входит в
  предмет проверки.

Артефакты: логи прогонов `/tmp/qa2-doctor/log-{1,2,3}.txt`, скриншоты `/tmp/qa2-doctor/shots/`,
SQLite-база прогона `/tmp/qa2-doctor/qa.sqlite`. Ни один файл в `app/` и `docs/` не изменялся,
кроме этого отчёта.

## Дефекты

### 1. Сводку пациента врач не может подтвердить — счётчик «Новых материалов» не обнуляется

Самое заметное. Врач не может снять последний материал, который сам же видит в списке.

Как выглядит. Пациент отправляет сводку, в списке пациентов появляется бейдж
«Новых материалов: 1». Врач открывает карточку, обходит все четыре вкладки и три подраздела
плана — кнопки подтверждения сводки нет нигде: 0 кнопок и 0 текстовых упоминаний сводки.
Вкладка «Обзор» её тоже не показывает: в `src/appointment.ts:46` список ожидающих жёстко
пустой — `const pendingReports:never[]=[]`.

Где три источника расходятся:

- **экран** — подтвердить сводку нечем;
- **API** — `GET /doctor/patients` возвращает `pending_reports: 1` и включает её в
  `pending_reports + pending_assessments + pending_practices + pending_goals`, то есть в тот
  самый бейдж «Новых материалов»;
- **база** — `reports.reviewed_at` остаётся `NULL`.

При этом серверный обработчик на месте и работает: прямой вызов
`POST /doctor/patients/:id/reports/:reportId/review` вернул 200, `reviewed_at` записался,
`pending_reports` стал 0 и бейдж «Новых материалов» упал с 4 до 0. То есть расходится именно
клиент: в `src/` нет ни одного обращения к `reports` и ни одного вызова этого маршрута.

Последствие. Счётчик непрочитанного у врача не может стать нулём у любого пациента, который
хотя бы раз прислал сводку. Он копится и всегда показывает работу, которую врач физически
не способен закрыть.

### 2. «Привычка пациента» и «Порядок просмотра записей» не доходят до пациента

Врач пишет в плане инструкцию для пациента, и она пропадает.

Как выглядит. В разделе «Отслеживаем» есть поля «Привычка пациента» и «Порядок просмотра
записей». Заполненные значения сохраняются, показываются при повторном открытии формы
у врача и уходят пациенту в API — но на экране пациента «План врача» их нет. Там выводится
только шкалы, практики, записи приёма и назначенные препараты.

Где три источника расходятся:

- **экран пациента** — привычки «Прогулка после ужина» и порядка просмотра нет ни на «Плане
  врача», ни на главной;
- **API** — `GET /patient/data` отдаёт `plan.habit` и `plan.reviewNote` полностью;
- **база** — оба поля лежат в `plans.data` без искажений.

Причина в клиенте: `src/Patient.tsx` из плана читает только `plan.sleep`, `plan.anxiety`,
`plan.energy`, `plan.functioning` и `plan.practices`; `plan.habit` (строка) и `plan.reviewNote`
не читаются нигде. Все совпадения `habit` в этом файле относятся к булеву полю `entry.habit`
отметки, а не к плану.

Последствие. Самое важное поле плана для пациента — что именно врач просит от него делать и
как читать записи — врач записывает, система хранит, но пациент его не видит. Для поля
«Порядок просмотра записей» это особенно заметно: врач объясняет пациенту, на что смотреть
в его же истории.

## Не удалось проверить

- **Текстовое содержимое PDF в CV. Проверено 13 октября.** Установлен `pdfjs-dist`, файл скачан из браузера и распарсен: страниц 1, 572 символа, все 11 введённых полей и 6 заголовков разделов извлекаются без подмен глифов, лишних маркеров (`undefined`, `NaN`, `?`) нет, расхождений 0. Имя файла, сигнатура `%PDF` и размер совпадают с прошлым замером.
  ~86 КБ, имя файла формируется из ФИО (`cv-кабылов-артур-дустович.pdf`). Внутреннее текстовое
  наполнение не сверялось: PDF собирается в браузере (`src/reportPdf.ts`), текст лежит в
  сжатых потоках, а `latin1`-чтение кириллицы его не показывает. Проверка требует парсера PDF.
- **CSV при дневнике длиннее 365 отметок.** Проверено на одном дневнике, где лимит
  `LIMIT 365` в `server/index.ts` не срабатывает. На длинном дневнике CSV выведет только
  последние 365 строк — это следует из кода, но не измерено.
- **Поведение без service worker.** В тестовом окружении он заблокирован, поэтому ветка
  с баннером установки PWA не проверялась.
- **Горизонтальная прокрутка на 320 px.** Один замер показал `scrollWidth=323` против
  `innerWidth=320` на экране профиля (3 px). При повторной проверке не воспроизвелось —
  считать дефектом нельзя, нужен отдельный воспроизводимый прогон.
- **Интерфейс администратора** (одобрение заявки, блокировка через UI) — по условиям задачи
  проверяет другой агент; здесь обе операции делались прямым SQL.
- **Защита от перебора пароля и троттлинг регистрации.** Не входили в предмет проверки;
  счётчики `auth_attempts` чистились перед каждым прогоном.

## Проверенные кейсы

1. **Регистрация врача и экран неподтверждённого специалиста.** Форма регистрации в браузере,
   выбор роли «Врач», создание аккаунта. Проверено, что кабинет врача не открывается: вместо
   списка пациентов — «Подключение врача» с формой заявки, в меню четыре пункта, ни одного
   пациента и ни одной кнопки «Пригласить пациента». Сверялось с тем, что реально разрешает
   сервер: приглашения 403, список пациентов 200 и пуст, `specialist_verified_at` и
   `specialty_kind` в базе `NULL`. Отдельно замерено `/code`: экран открыт неподтверждённому
   врачу и предлагает «Создать ссылку», сервер отвечает 403 — действие недоступно, но
   оформлено как обычная рабочая кнопка без предупреждения.

2. **Заявка на проверку.** Отправка формы, статус `pending` в экране, API и базе. Перевод
   заявки в `needs_info` прямым SQL: комментарий администратора из базы показан на экране,
   форма снова доступна. Повторная отправка обновляет ту же строку (не плодит новые), номер
   лицензии заменяется, статус снова `pending`, `admin_note` сохраняется в базе.
   Косметическое замечание: подпись «Заявка отправлена» не появляется — она находится внутри
   формы, а форма скрывается сразу после успешной отправки. Подтверждением служит баннер
   «Заявка на проверке», он соответствует данным.

3. **Приглашения.** Создание из `/code`, срок 7 дней совпадает в экране («Действует до
   20 октября 2026 г.») и в `invites.expires`. Одноразовость: принятие первым пациентом →
   `used=1`, `raw=NULL`; попытка принять тем же токеном другим → 404, в `links` новая строка
   не появляется. Отзыв кнопкой: строка исчезает из списка, токен стирается, повторно открыть
   нельзя. Просроченное приглашение не открывается (404) и не показывается как активное.

4. **Подключение пациента.** Пациент открывает ссылку, видит профиль врача, подтверждает
   согласие. Появляются `links` с `accepted_at` и `revoked_at=NULL`, в `invites` выставляется
   `used=1`. Пациент видит «Имеет доступ к вашей истории» и имя врача. Список пациентов у
   врача на экране совпал с активными связями в базе. Повторное принятие приглашения при уже
   подключённом враче отклонено (409 «У вас уже подключён врач…»), лишней строки в `links` нет.

5. **Список пациентов: фильтры и поиск.** Подготовлено шесть пациентов с разным состоянием:
   без отметок; две отметки, последняя пять дней назад с самочувствием 1; свежая отметка и
   шесть непрочитанных материалов; три ровные отметки без материалов; два без данных.
   Все три фильтра показали ровно тот состав, который даёт база: «Требуют внимания» 4 из 6,
   «Новые материалы» 1 из 6, «Без отметок» 3 из 6, «Все пациенты» 6 из 6. По каждому пациенту
   отдельно сошлись число отметок, дата последней отметки и все четыре счётчика непрочитанного
   между API и SQL. Бейдж «Новых материалов: N» равен сумме непрочитанного в базе. Поиск
   работает по имени, по префиксу фамилии и в нижнем регистре для кириллицы («остро» находит
   «Острова Мадина»); на несуществующий запрос — «Ничего не найдено».

6. **Вкладки карточки пациента.** Каждая вкладка отдаёт свои данные: «Обзор» — «Перед приёмом»,
   «Цели» — «Личные цели пациента» с отметками, «История» — «Опыт практик» и записи по дням,
   «План наблюдения» — «Отслеживаем». Число отметок в карточке совпало с `entries` в API и с
   `checkins` в базе.

7. **Подтверждение просмотра: одиночное и пакетное.** Одиночное подтверждение отзыва: на
   нажатой записи появились `reviewed_at` и `reviewer_id` этого врача, счётчик
   `pending_practices` уменьшился с 3 до 2, пакетная кнопка пересчиталась с «Подтвердить все (3)»
   на «Подтвердить все (2)» — интерфейс не предлагает подтвердить уже подтверждённое. Пакетное
   подтверждение обнулило счётчик, в базе все три записи с `reviewed_at` и `reviewer_id` этого
   врача, кнопка исчезла. Повторное подтверждение той же записи через API не изменило
   `reviewed_at` (COALESCE) и не сломало счётчики. Отметки по целям: «Подтвердить все
   непрочитанные» закрыло обе записи, `pending_goals` стал 0, кнопка исчезла. Результат
   опросника: `reviewed_at` записан, `pending_assessments` стал 0. **Сводка — дефект № 1.**

8. **План наблюдения, «Отслеживаем».** Выставлена частота «Раз в неделю», включена шкала
   «Энергия», снята «Сон», выбраны две практики из двенадцати, заполнены привычка и порядок
   просмотра. Экран показал «План сохранён»; `GET /doctor/patients/:id/data`, `plans.data`
   и ответ пациенту совпали между собой и с ожидаемыми значениями по всем полям. После
   перезагрузки карточки форма показала сохранённые частоту, привычку и порядок просмотра.
   **Передача пациенту — дефект № 2:** API отдаёт поля, экран пациента их не показывает.

9. **Опросники.** Конструктор: заполнены название, инструкция, методика и источник, добавлены

13. **Блокировка врача администратором.** Врача с одним пациентом заблокировали прямым SQL.
    Все его запросы закрылись: `/me`, список пациентов, карточка пациента и создание приглашения
    вернули 401, повторный вход — 403 «Аккаунт заблокирован. Обратитесь к администратору».
    Проверены два пути на экране. Путь «внутри кабинета»: следующий запрос возвращает 401, и
    врач видит «Сеанс завершён. Войдите снова.» — правильно. Путь «перезагрузка»: врач молча
    оказывается на форме входа без объяснения, потому что запрос `/me` в `src/api.ts`
    исключён из события `session-expired`. Данные пациента не пострадали: его `GET /patient/data`
    остался 200. Замечено, что блокировка не разрывает связь: в `links` остаётся `revoked_at=NULL`,
    и пациент по-прежнему видит имя заблокированного врача в своей карточке.
