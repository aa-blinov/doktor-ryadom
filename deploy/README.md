# Docker и общий Caddy

Приложение собирается в один контейнер: Node.js обслуживает PWA и API, SQLite хранит аккаунты, сессии, планы и записи в постоянном томе `ryadom_data`. Cloudflare и D1 для этого способа запуска не нужны. Миграции применяются при запуске один раз; изменение уже применённого SQL-файла останавливает запуск.

## Конфигурация сервера

Существующий прокси описан в `/home/ubuntu/infra/caddy/docker-compose.yml`: контейнер `edge-caddy`, внешняя сеть `edge`, подсеть `172.40.0.0/24`, TLS через DuckDNS. Приложение использует `172.40.0.30:3000`. Этот адрес отсутствует в таблице проектов Caddy, но занятость нужно проверить через Docker перед запуском.

```sh
docker network inspect edge --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{println}}{{end}}'
docker compose config --quiet
docker compose up -d --build
docker compose ps
docker compose logs --tail 50 app
```

Команды выполняются из корня этого проекта. Если `.30` занят, выберите свободный адрес через `RYADOM_EDGE_IP` и измените адрес в блоке Caddy. Порт приложения не публикуется на хосте: запросы приходят через общую сеть прокси.

## Подключение домена

Добавьте содержимое [Caddyfile.fragment](Caddyfile.fragment) в существующий `/home/ubuntu/infra/caddy/Caddyfile`. Не заменяйте весь файл: он обслуживает другие проекты. Блок использует уже настроенные `duckdns_tls` и `proxy_headers`. Токен DuckDNS остаётся в конфигурации общего Caddy.

Готовый скрипт проверяет конфигурацию, сохраняет резервную копию и добавляет блок без замены остальных сайтов:

```sh
bash deploy/persist-caddy.sh
```

Скрипт требует права записи в общий Caddyfile. Его повторный запуск не добавляет второй блок. Затем можно проверить конфигурацию и перечитать её без остановки сайтов:

```sh
docker exec edge-caddy caddy validate --config /etc/caddy/Caddyfile
docker exec edge-caddy caddy reload --config /etc/caddy/Caddyfile
curl --fail https://doktor-ryadom.duckdns.org/api/health
```

`PUBLIC_ORIGIN` в Compose задаёт HTTPS-домен для проверки Origin и защищённых cookie. При смене домена обновите его вместе с Caddyfile. Для работы сертификата сервер должен быть доступен по 80/443, а существующий DuckDNS-токен должен разрешать работу с этим поддоменом.

## Данные и обновление

```sh
docker compose up -d --build
```

Обновление сохраняет том с базой. `docker compose down` также сохраняет данные; добавление `-v` удаляет том и записи. Для резервной копии SQLite используйте механизм SQLite backup, а не копирование одного файла во время записи: база работает в режиме WAL.

Образ приложения собран и развёрнут командами `docker compose build` и `docker compose up -d app backup`. Перед пересозданием создана SQLite-копия, прошедшая проверки целостности. Контейнер приложения и сервиса резервных копий — `healthy`; `/api/health`, главная страница, новый JS-бандл и ресурсы PDF проверены через работающий маршрут Caddy.

Маршрут `doktor-ryadom.duckdns.org` есть в активной конфигурации и autosave Caddy, но отсутствует в `/home/ubuntu/infra/caddy/Caddyfile`. Процесс Caddy использует Caddyfile без `--resume`; после перезапуска прокси маршрут может исчезнуть. Добавьте `deploy/Caddyfile.fragment` в общий файл, затем выполните `caddy validate` и `caddy reload` по инструкции выше.

Образ собран через Docker Compose, контейнер `doktor-ryadom` запущен и имеет статус healthy. Сборка Node/PWA и 17 тестов проходят, включая сохранность SQLite и сессии после повторного открытия базы. Главная страница и `/api/health` на HTTPS-домене возвращают 200.

Маршрут применён через рабочую конфигурацию общего Caddy, без перезапуска прокси. Исходный `/home/ubuntu/infra/caddy/Caddyfile` не изменён: автоматическая проверка разрешений отклонила запись вне каталога проекта. Caddy запускается с этим исходным файлом, поэтому после его перезапуска маршрут нового домена исчезнет, пока блок не добавлен в файл. Для постоянного подключения выполните `bash deploy/persist-caddy.sh` из сессии с правом записи в общий Caddyfile. Не перезапускайте общий Caddy до этого шага.

## Почта и проверка врача

Скопируйте `.env.example` в `.env` и заполните SMTP-параметры и `RYADOM_MAIL_FROM` либо ключ Resend и отправителя. После изменения выполните `docker compose up -d`. Без отправителя кнопки отправки писем недоступны; сброс по резервному коду работает отдельно. Проверьте доставку на тестовом аккаунте.

После проверки квалификации специалиста администратор выполняет:

```sh
docker compose exec app node scripts/verify-specialist.mjs --email doctor@example.com --qualification-checked
```

Для снятия подтверждения используйте `--revoke`. Не подтверждайте квалификацию только по выбранной при регистрации роли.

## Резервные копии

Ежедневные проверенные копии находятся в `/data/backups/`, срок хранения — семь дней. Ключи VAPID сохраняются в `/data/vapid.json`; не публикуйте этот файл. Подключите независимую копию вне сервера с размещением, согласованным для Казахстана.

Восстановление выполняется при остановленном приложении: сохраните текущую базу и её WAL/SHM, проверьте выбранную копию командой SQLite `PRAGMA integrity_check`, восстановите её как `/data/ryadom.sqlite`, удалите только старые WAL/SHM восстановленной базы и запустите контейнер. Перед операцией проверьте путь базы в Compose и `server/node.ts`; не восстанавливайте копию поверх работающей базы. Проверка восстановления в тестах не заменяет проверку внешних копий.

Почта подключена через Яндекс SMTP с TLS на 465. Проверены авторизация и принятие тестового письма сервером (250 OK). Учётные данные хранятся в локальном `.env` с правами 0600; в архив они не включаются.
